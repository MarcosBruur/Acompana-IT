# Acompañamiento IT

Base del prototipo de la **Plataforma de acompañamiento en la inserción laboral de jóvenes en tecnología** (TFG, Universidad Siglo 21). Esta entrega prepara frontend, API y esquema de datos; las funcionalidades de las HU-001 a HU-013 se incorporarán por iteraciones.

## Requisitos

- Python 3.13 y [`uv`](https://docs.astral.sh/uv/)
- Node.js 20.19+ o 22.12+ y npm (Vite latest)
- Docker Desktop con motor iniciado para PostgreSQL + pgvector

## Inicio local

En tres terminales, desde la raíz del proyecto:

```powershell
docker compose up -d db
```

El PostgreSQL del contenedor se publica en `127.0.0.1:5433` para no interferir con una instalación local que utilice el puerto `5432`.

```powershell
cd backend
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

```powershell
cd frontend
npm install
npm run dev
```

Abrir http://localhost:5173. La API está en http://localhost:8000/docs y su prueba de disponibilidad en http://localhost:8000/api/v1/health. Vite redirige `/api` al backend local; el frontend indica el estado de conexión en la pantalla principal.

Para configurar otros puertos o credenciales, copiar `backend/.env.example` a `backend/.env` y ajustar `DATABASE_URL` y `FRONTEND_ORIGIN`. Para apuntar el frontend a otro servidor, copiar `frontend/.env.example` a `frontend/.env` y definir `VITE_API_URL`. No subir archivos `.env` al repositorio.

```text

│   ├── app/modules/       # Dominios funcionales del proyecto

│   ├── pyproject.toml     # Dependencias uv
│   └── uv.lock
└── frontend/
    ├── src/features/      # Catálogo de módulos
    ├── src/pages/         # Vistas iniciales
    ├── src/services/      # Acceso a la API
    ├── package.json
    └── package-lock.json
```

El backend incluye modelos de candidatos, sesiones, identidades Google, CV, vacantes y los demás módulos; el esquema se aplica con Alembic. El endpoint de salud no requiere base de datos. Registro, inicio de sesión, perfil, carga de CV y análisis de vacantes funcionan con la API. Las comparaciones y las entrevistas siguen siendo vistas de ejemplo.

Los IDs de las entidades son enteros autoincrementales (`GENERATED BY DEFAULT AS IDENTITY` en PostgreSQL); sus claves foráneas son enteras. La migración `0003_integer_ids` convierte IDs UUID anteriores sin borrar registros y actualiza las relaciones. La tabla `alembic_version` conserva los identificadores textuales de revisiones.

## Cuentas y acceso

- Inicio y análisis de nuevas vacantes son públicos. El historial de análisis guardados requiere sesión del propietario. Comparaciones y entrevistas requieren sesión; sus endpoints funcionales aún no existen y, al implementarlos, deberán comprobar la propiedad de los datos.
- Registro e inicio de sesión: `/registro` y `/sesion`. La contraseña exige al menos 8 caracteres, una mayúscula, un número y un carácter especial. En registro y cambio de contraseña la confirmación es obligatoria y se comprueba también en la API. Se almacena como hash Argon2id con sal. A los 200 días, el candidato debe cambiarla en `/cambiar-contrasena` por una distinta antes de acceder a funciones protegidas. La cuenta Google no tiene contraseña local.
- Las sesiones duran siete días: se almacena el hash de un token aleatorio en la base de datos y se usa una cookie HttpOnly, SameSite=Lax. Cerrar sesión revoca la sesión actual; cambiar contraseña revoca todas las sesiones anteriores. Para HTTPS, configurar `COOKIE_SECURE=true`. Las solicitudes mutantes a `/api/v1` requieren un `Origin` igual a `FRONTEND_ORIGIN` o `BACKEND_ORIGIN`.
- Para habilitar Google, crear credenciales OAuth de tipo **aplicación web** en Google Cloud, configurar la pantalla de consentimiento y autorizar el URI `http://localhost:8000/api/v1/auth/google/callback`. En `backend/.env` configurar `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` y, para otros entornos, `BACKEND_ORIGIN` y el URI correspondiente en Google Cloud. El botón solo se habilita cuando hay credenciales. No se vincula automáticamente una identidad Google a una cuenta local que ya use el mismo correo; en ese caso, iniciar sesión con contraseña.
- Usar el mismo host para navegador y `BACKEND_ORIGIN` (por ejemplo `localhost` en ambos). En producción, frontend y backend deben compartir sitio y usar HTTPS para que funcionen las cookies. Mantener `VITE_API_URL` apuntando a `/api/v1` o a una API del mismo sitio.

## Perfil y archivos

- `/perfil` requiere una cuenta activa. Permite cambiar el apodo, recortar y guardar una foto, cargar varios PDF (máximo 5 MB cada uno) arrastrándolos o seleccionándolos, consultar el CV principal y elegir otro como principal. El encabezado muestra el apodo y la foto guardados. La antigua ruta `/curriculum` redirige a `/perfil`.
- Los archivos privados se almacenan en `backend/app/media/images/AAAA_MM_DD/imagen_<identificador>.webp` y `backend/app/media/files/AAAA_MM_DD/cv_<identificador>.pdf`. Las carpetas se crean al cargar archivos; nunca se guardan binarios en la base de datos ni se sirven desde Vite. `MEDIA_DIR` permite cambiar la ubicación para usar un volumen persistente. Las descargas y la foto requieren sesión del propietario.
- Conservar y respaldar el directorio de medios junto con PostgreSQL. `.gitignore` excluye `backend/app/media/`.

## Análisis de vacantes con OpenAI

- Copiar `backend/.env.example` a `backend/.env` y configurar `OPENAI_API_KEY` con una clave válida de OpenAI. `OPENAI_MODEL` es opcional (predeterminado `gpt-4.1-mini`, debe admitir salida estructurada mediante JSON Schema). Reiniciar el backend después de configurar la clave. **No** agregarla a `frontend/.env` ni subirla a Git. Sin clave, el formulario informa que el servicio aún no está configurado.
- La clave debe pertenecer a un proyecto de OpenAI con créditos o facturación disponibles. Si el proveedor responde `credit_balance_exhausted`, la API informa que falta saldo; revisá la facturación y los límites del proyecto de esa clave antes de reintentar.
- `/vacantes` permite analizar texto plano (título, empresa opcional y descripción de 30 a 12000 caracteres) sin CV. El endpoint `POST /api/v1/vacancies/analyze` envía exclusivamente esos datos a OpenAI mediante LangChain; por tanto, evitá incluir información privada en la oferta pegada. Un análisis anónimo solo se mantiene en la página actual; recargarla lo pierde. Si hay sesión activa, se guardan oferta y resultado en PostgreSQL y se consultan en `GET /api/v1/vacancies` y `GET /api/v1/vacancies/{id}` (solo propietario).
- El riesgo porcentual es **orientativo**: suma 30/15/5 puntos por alerta con evidencia textual de relevancia alta/media/baja, máximo 100. No indica compatibilidad con un candidato ni garantías sobre la empresa. El servidor descarta alertas cuya cita no figure en la oferta. Los resultados se validan antes de guardarse o mostrarse.
- Para acotar consumo: máximo 10 análisis anónimos por IP y 30 por cuenta en una hora, hasta 3 llamadas simultáneas por proceso, 2000 tokens de salida y 30 segundos por llamada. El límite de frecuencia es en memoria **por proceso**; en un despliegue con varios procesos/instancias conviene un limitador compartido en el proxy o Redis y presupuestos de uso configurados en OpenAI.
