# CHOOMIT

Base del prototipo de la **Plataforma de acompañamiento en la inserción laboral de jóvenes en tecnología** (TFG, Universidad Siglo 21). Esta entrega prepara frontend, API y esquema de datos; las funcionalidades de las HU-001 a HU-013 se incorporarán por iteraciones.

## Requisitos

- Python 3.13 y [`uv`](https://docs.astral.sh/uv/)
- Node.js 20.19+ o 22.12+ y npm (Vite latest)
- Docker Desktop con motor iniciado para PostgreSQL + pgvector; Redis opcional para límites compartidos

## Inicio local

En tres terminales, desde la raíz del proyecto:

```powershell
docker compose up -d db redis
```

PostgreSQL se publica en `127.0.0.1:5433` y Redis en `127.0.0.1:6379`, solo para desarrollo local. En `backend/.env` definir `REDIS_URL=redis://127.0.0.1:6379/0` para habilitar los límites compartidos. Sin esta variable los límites siguen funcionando por proceso; si se configura Redis y deja de estar disponible, la API rechaza las operaciones limitadas con 503 en vez de omitir la protección.

```powershell
cd backend
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

```powershell
cd frontend
npm install
npm run dev
```

Abrir http://localhost:5173. La API está en http://localhost:8000/docs. `/api/v1/health` comprueba que el proceso responda; `/api/v1/ready` comprueba además la conexión a PostgreSQL. Vite redirige `/api` al backend local.

Para configurar otros puertos o credenciales, copiar `backend/.env.example` a `backend/.env` y ajustar `DATABASE_URL` y `FRONTEND_ORIGIN`. Para apuntar el frontend a otro servidor, copiar `frontend/.env.example` a `frontend/.env` y definir `VITE_API_URL`. No subir archivos `.env` al repositorio.

## Estructura

```text
.
├── AGENTS.md              # Requisitos del TFG, convenciones y decisiones
├── compose.yaml           # PostgreSQL y Redis (solo entorno local)
├── backend/
│   ├── app/api/           # Endpoints FastAPI
│   ├── app/core/          # Configuración
│   ├── app/db/            # Modelos SQLAlchemy y conexión
│   ├── app/modules/       # Dominios funcionales del proyecto
│   ├── alembic/           # Migraciones versionadas
│   ├── pyproject.toml     # Dependencias uv
│   └── uv.lock
└── frontend/
    ├── src/features/      # Catálogo de módulos
    ├── src/pages/         # Vistas iniciales
    ├── src/services/      # Acceso a la API
    ├── package.json
    └── package-lock.json
```

El backend incluye modelos de candidatos, sesiones, identidades Google, CV, vacantes y los demás módulos; el esquema se aplica con Alembic. El endpoint de salud no requiere base de datos. Registro, inicio de sesión, perfil, carga de CV, análisis de vacantes y entrevistas funcionan con la API. Las comparaciones siguen siendo vistas de ejemplo.

Los IDs de las entidades son enteros autoincrementales (`GENERATED BY DEFAULT AS IDENTITY` en PostgreSQL); sus claves foráneas son enteras. La migración `0003_integer_ids` convierte IDs UUID anteriores sin borrar registros y actualiza las relaciones; su *downgrade* genera UUID nuevos y **no recupera los originales**, por lo que para datos reales se debe restaurar un respaldo en vez de revertirla. La tabla `alembic_version` conserva los identificadores textuales de revisiones. `0011_audit_integrity` añade restricciones e índices; `0012_comparison_ownership` impide guardar comparaciones entre propietarios distintos; `0013_candidate_admin` agrega `candidates.admin` (false por defecto). Si ya hay entrevistas duplicadas, estados inválidos o comparaciones cruzadas, corregir esos datos antes de migrar, sin borrarlos automáticamente.

## Cuentas y acceso

- Inicio y análisis de nuevas vacantes son públicos. El historial de análisis guardados y las entrevistas requieren sesión del propietario. Comparaciones aún no tiene endpoints funcionales.
- Registro e inicio de sesión: `/registro` y `/sesion`. La contraseña exige al menos 8 caracteres, una mayúscula, un número y un carácter especial. En registro y cambio de contraseña la confirmación es obligatoria y se comprueba también en la API. Se almacena como hash Argon2id con sal. A los 200 días, el candidato debe cambiarla en `/cambiar-contrasena` por una distinta antes de acceder a funciones protegidas. La cuenta Google no tiene contraseña local.
- Las sesiones duran siete días: se almacena el hash de un token aleatorio en la base de datos y se usa una cookie HttpOnly, SameSite=Lax. Cerrar sesión revoca la sesión actual; cambiar contraseña revoca todas las sesiones anteriores; una cuenta con `active=false` no puede iniciar ni mantener sesión. Registro, inicio, cambio de contraseña, análisis y entrevistas tienen límites por cuenta/IP; con `REDIS_URL` son compartidos entre procesos. Para HTTPS, configurar `COOKIE_SECURE=true`. Las solicitudes mutantes a `/api/v1` requieren un `Origin` igual a `FRONTEND_ORIGIN` o `BACKEND_ORIGIN`; el canal WebSocket de voz exige el origen del frontend.
- Cupos en PostgreSQL para candidatos no administradores: 5 CV activos, 20 vacantes analizadas activas, 10 entrevistas iniciadas en cualquier ventana móvil de 24 horas (aunque se cancelen u oculten) y 20 resultados completados visibles. Ocultar un CV, una vacante o un resultado libera el cupo de almacenamiento respectivo. Con 20 resultados visibles debe ocultarse uno antes de iniciar otra entrevista. `candidates.admin=true`, asignado exclusivamente en el servidor, exime de estos cupos, pero no de autenticación, controles de concurrencia o límites de voz. La API informa en español cuando se supera cada cupo.
- Para habilitar Google, crear credenciales OAuth de tipo **aplicación web** en Google Cloud, configurar la pantalla de consentimiento y autorizar el URI `http://localhost:8000/api/v1/auth/google/callback`. En `backend/.env` configurar `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` y, para otros entornos, `BACKEND_ORIGIN` y el URI correspondiente en Google Cloud. El botón solo se habilita cuando hay credenciales. No se vincula automáticamente una identidad Google a una cuenta local que ya use el mismo correo; en ese caso, iniciar sesión con contraseña.
- Usar el mismo host para navegador y `BACKEND_ORIGIN` (por ejemplo `localhost` en ambos). En producción, frontend y backend deben compartir sitio y usar HTTPS para que funcionen las cookies. Mantener `VITE_API_URL` apuntando a `/api/v1` o a una API del mismo sitio.

## Perfil y archivos

- `/perfil` requiere una cuenta activa. Permite cambiar el apodo, recortar y guardar una foto, cargar hasta 5 PDF activos por candidato (máximo 5 MB cada uno) arrastrándolos o seleccionándolos, consultar el CV principal y elegir otro como principal. Ocultar un CV libera un lugar sin eliminar el archivo. El encabezado muestra el apodo y la foto guardados. La antigua ruta `/curriculum` redirige a `/perfil`.
- Los archivos privados se almacenan en `backend/app/media/images/AAAA_MM_DD/imagen_<identificador>.webp` y `backend/app/media/files/AAAA_MM_DD/cv_<identificador>.pdf`. Las carpetas se crean al cargar archivos; nunca se guardan binarios en la base de datos ni se sirven desde Vite. `MEDIA_DIR` permite cambiar la ubicación para usar un volumen persistente. Las descargas y la foto requieren sesión del propietario.
- Conservar y respaldar el directorio de medios junto con PostgreSQL. `.gitignore` excluye `backend/app/media/`. En `backend/`, ejecutar `uv run python -m app.core.media_maintenance` para contar referencias ausentes y archivos huérfanos sin mostrar nombres; `--delete-orphans` elimina **solo** archivos generados por la plataforma, sin referencia y con más de 24 horas, y no elimina nada si hay referencias perdidas. Los PDF se comprueban y se leen en un proceso separable con tiempo máximo de 10 segundos y límite de 256 MB de memoria (`PDF_TIMEOUT_SECONDS`, `PDF_MEMORY_MB` configurables) sin cambiar el máximo de 5 MB del archivo.

Para generar respaldos PostgreSQL (`pg_dump` en formato custom) y medios privados (`tar.gz`), configurar **`BACKUP_DIR` fuera del repositorio y de `MEDIA_DIR`** y ejecutar desde `backend/` `uv run python -m app.core.backup`. Si `pg_dump` está disponible en el host se usa directamente (opcional `PG_DUMP_PATH`); en el entorno Docker local sin `pg_dump` en el host configurar también `BACKUP_DB_CONTAINER=tfg-db-1`. Probar restauración en una base aislada, establecer permisos privados sobre el directorio de respaldo y programar la ejecución diaria según el servidor/Task Scheduler. La copia física quincenal exige que indiques el destino externo; no se programa ni se envía automáticamente a un destino desconocido.

## Modelos de OpenAI para vacantes y entrevistas

- Copiar `backend/.env.example` a `backend/.env` y configurar `OPENAI_API_KEY` con una clave válida de OpenAI. Para probar modelos distintos, descomentar y cambiar estas líneas en **`backend/.env`**:

  ```dotenv
  OPENAI_VACANCY_MODEL=gpt-4.1-mini
  OPENAI_INTERVIEW_MODEL=gpt-4.1-mini
  ```

  `OPENAI_VACANCY_MODEL` se usa al analizar ofertas. `OPENAI_INTERVIEW_MODEL` se usa tanto al generar preguntas como al corregir respuestas conversacionales. Cada variable es opcional: si falta o está vacía, se usa `OPENAI_MODEL`; si este tampoco está definido, el predeterminado es `gpt-4.1-mini`. Así, una configuración anterior con solo `OPENAI_MODEL` sigue funcionando. Editar el nombre del modelo elegido y **reiniciar el backend** para probar otro; cambiar `.env` no recarga automáticamente la configuración, incluso con `uvicorn --reload`. Los modelos deben estar disponibles para la clave usada y admitir salida estructurada mediante JSON Schema estricto. Para modelos de razonamiento como `gpt-6-luna` y `gpt-6.1-terra` no se envía `temperature=0`, que OpenAI rechaza con la configuración de razonamiento predeterminada; en modelos no razonadores se conserva `temperature=0`. La clave y los modelos se configuran solo en el backend: **no** agregarlos a `frontend/.env` ni subir `backend/.env` a Git. Sin clave, los formularios informan que el servicio aún no está configurado.
- La clave debe pertenecer a un proyecto de OpenAI con créditos o facturación disponibles. Si el proveedor responde `credit_balance_exhausted`, la API informa que falta saldo; revisá la facturación y los límites del proyecto de esa clave antes de reintentar.
- `/vacantes` permite analizar texto plano (título, empresa opcional y descripción de 30 a 12000 caracteres) sin CV. El endpoint `POST /api/v1/vacancies/analyze` envía exclusivamente esos datos a OpenAI mediante LangChain; por tanto, evitá incluir información privada en la oferta pegada. Un análisis anónimo solo se mantiene en la página actual; recargarla lo pierde. Si hay sesión activa, se guardan oferta y resultado en PostgreSQL y se consultan en `GET /api/v1/vacancies` y `GET /api/v1/vacancies/{id}` (solo propietario).
- El riesgo porcentual es **orientativo**: suma 30/15/5 puntos por alerta con evidencia textual de relevancia alta/media/baja, máximo 100. No indica compatibilidad con un candidato ni garantías sobre la empresa. El servidor descarta alertas cuya cita no figure en la oferta. Los resultados se validan antes de guardarse o mostrarse.
- Para acotar consumo: máximo 10 análisis anónimos por IP y 30 por cuenta en una hora, hasta 3 llamadas simultáneas por proceso, 2000 tokens de salida y 30 segundos por llamada. Los fallos técnicos de proveedor o por capacidad devuelven el cupo de la solicitud. Con `REDIS_URL` la ventana deslizante es atómica y compartida entre procesos; sin configurar Redis se usa un límite local depurado periódicamente. La concurrencia de llamadas sigue siendo por proceso; configurar presupuestos de uso en OpenAI para el despliegue.

## Voz natural en entrevistas

- En el modo conversación solo se acredita como correcta una respuesta técnicamente completa. Cuando lo es, no se genera ni guarda una respuesta modelo: tras una pausa de unos 900 ms se presenta el enlace breve y la siguiente pregunta. Una respuesta parcial recibe una corrección breve y suma medio punto; incorrecta u omitida suma cero. Las correcciones usan lenguaje natural, conceptos y ejemplos narrativos relacionados con la vacante, sin fragmentos de código literales en el chat, la voz ni el resultado guardado. Si el proveedor devuelve código en una corrección, el backend intenta reformularla una vez antes de aceptarla; si persiste, no guarda esa respuesta. Para preguntas conversacionales omitidas, el resultado propone repasar el tema sin copiar la respuesta de referencia, que podría contener código. La nota se calcula sobre todas las preguntas e identifica parciales y omitidas en el resultado.
- La voz del entrevistador usa OpenAI Realtime mediante un WebSocket mediado por el backend en entrevistas conversacionales (predeterminado `gpt-realtime-2.1-mini`, voz `marin`). El backend envía audio PCM al navegador, donde se reproduce con Web Audio; la clave del proveedor nunca sale del servidor. Para cambiar el modelo/voz, configurar opcionalmente `OPENAI_VOICE_MODEL` y `OPENAI_VOICE` en `backend/.env` y reiniciar el backend. Se requiere acceso al modelo Realtime elegido y saldo para audio.
- Cada intervención de voz incluye instrucciones de español rioplatense y entonación argentina natural; las instrucciones por intervención reemplazan las de la sesión, por eso se especifican en ambos lugares. El acento se orienta por instrucciones, no existe una voz integrada denominada «argentina» ni se garantiza una copia exacta de las voces de ChatGPT. Para comparar timbres, probar `OPENAI_VOICE=marin` y `OPENAI_VOICE=cedar`; si el acento no resulta convincente, probar `OPENAI_VOICE_MODEL=gpt-realtime-2`, que puede seguir indicaciones de acento con más fidelidad (con distinto costo). Reiniciar el backend e iniciar una nueva sesión de entrevista para escuchar los cambios.
- `WS /api/v1/interviews/{id}/voice` exige cookie válida, origen autorizado, entrevista conversacional propia en curso y hasta ocho conexiones por cuenta y hora. El navegador envía **identificadores de fragmentos**, nunca texto libre: el servidor reconstruye exclusivamente preguntas, correcciones y transiciones autorizadas desde la base de datos y envía solo ese texto a OpenAI. La respuesta PCM se transmite al navegador, sin guardar audio ni enviar CV o micrófono por este canal. El endpoint antiguo de token efímero ya no existe. La evaluación de respuestas sigue siendo exclusivamente del backend.
- El micrófono sigue usando reconocimiento de voz del navegador (que puede enviar audio a su servicio de transcripción); el chat escrito permanece disponible. Si WebSocket, el proveedor o la reproducción fallan, la sesión continúa por texto. Al desactivar la voz se interrumpe el audio; al salir se cierra la conexión. La voz generada intenta leer exactamente el texto guardado, aunque puede variar en la pronunciación. El costo del audio se suma al de generación y evaluación de texto.

## Comprobaciones

```powershell
cd backend
uv run ruff check .
uv run pytest
uv run python -c "from app.main import app; print(app.title)"
```

Para probar índices y restricciones con el motor de producción, crear una **base aislada** cuyo nombre empiece por `tfg_audit_`, configurarla mediante `DATABASE_URL` y ejecutar `uv run alembic upgrade head` y `uv run alembic check`. Después, definir `TEST_DATABASE_URL` apuntando a esa misma base y ejecutar `uv run pytest tests/test_postgres_integrity.py`; la prueba revierte sus inserciones. No ejecutar estos comandos contra la base principal para probar migraciones.

```powershell
cd frontend
npm run lint
npm run build
npm run test:e2e
```

La primera vez, instalar el navegador para las pruebas con `npx playwright install chromium`. Las pruebas interceptan la API y la voz, sin usar credenciales de OpenAI.
